# 依頼109：オウル件の対策の設計と実装 報告書（アント）

2026-11-26 ／ アント（Claude Code）

## 結論

- **対策A（Codexのエラー出力をログに残す）を、両方のワーカーに実装しました。** 未コミットのまま作業コピーに置いています。
- 対策Bは案を3つ出し、**推奨は案2（未保存の変更を退避ブランチへ保存して進む）** です。
- 対策Cは案を2つ出し、**推奨は「実行後に指示書の変更を検知して戻し、報告に載せる」** です。文案も添えました。
- 反映（コミット・push）は、報告書の後にモコ側で行う前提です。

## 理由（重要な順）

1. Codexの失敗理由が、ログに残らない状態でした（`2>$null` で捨てていた）。これが原因の切り分けを遅らせていました。
2. 未保存の変更で止まる仕組みは、人の確認が毎回必要になるため、退避して進める形が必要です。
3. 指示書の自己変更は、ワーカーが自分のルールを書き換えられる状態が根本です。検知と保留で線を引きます。

## 1. 対策A：実施結果

### 変更内容

- 変更ファイル：`worker/Invoke-CodexWorker.ps1`、`worker/Invoke-CodexWorker2.ps1`（両方、同じ変更）
- Codexの呼び出しで、エラー出力を捨てず、**実行ごとのファイル** に保存するようにしました。
  - 保存先：`logs/<依頼名>-<実行ID>-Codexエラー.txt`（logs はGit対象外）
  - 変更前：`2>$null`（捨てる）／変更後：`2>$errPath`（保存する）
- 失敗した時は、エラー出力の **末尾30行** を worker のログに書き出す関数を追加しました（`Write-CodexErrorLog`）。
- 通常の完了の流れ（出力の読み取り、報告書の作成、commit・push）は変更していません。

### テスト結果

|---|---|

### 未確認の点（要確認）

## 2. 対策B：未保存の変更や重複で止まらない仕組み（案のみ・未実施）

### 前提

- ファイルは削除しません。退避（別の場所への移動、または別ブランチへの保存）は可とします。
- お金・対人・認証情報が絡む詰まりは、従来どおり止めて報告します。

### 案1：退避フォルダへ移して進む（104の案B）

- **やり方**：未保存の変更を `logs/退避/<日時>/` へコピーし、作業ツリーを最新の状態に戻して次の依頼へ進みます。重複時は依頼を processed へ移して進みます（104の案B）。
- **良い点**：変更が手元に残り、ワーカーが止まりません。実装が一番小さくて済みます。
- **危ない点**：Gitの履歴に残らないため、後から差分を追いにくいです。退避フォルダが増え続けます。
- **作業時間の目安**：1〜2時間（推測）

### 案2：退避ブランチへ保存して進む（推奨）

- **やり方**：未保存の変更を `worker-退避/<日時>` のブランチへ commit して push します。main の作業ツリーは最新の状態に戻し、次の依頼へ進みます。
- **良い点**：変更が Git に残り、`git diff` で差分を確認できます。消えず、後で取り込みもしやすいです。
- **危ない点**：ブランチが増えるため、整理の決まりが要ります。指示書の変更を自動で保存すると、確認なしに残るため、**指示書（AGENTS.md類）は案2の対象外にして保留する**必要があります（対策Cと組み合わせる）。
- **作業時間の目安**：3〜4時間（推測）
- **推奨の理由**：消さずに、差分が見え、後から判断できるためです。

### 案3：止める（現状維持）＋保留報告を自動で作る

- **やり方**：未保存の変更があれば、従来どおり止めます。ただし、保留報告書を自動で作り、何が止まっているかを報告に必ず載せます。
- **良い点**：一番安全で、実装も小さいです（30分〜1時間・推測）。
- **危ない点**：止まり続けるため、人の確認が毎回必要です。今回の件（定時実行が連続で止まる）は解消しません。

### 親方の判断が要る点

- 案2を採るなら、**退避ブランチを GitHub へ push する**ことになります。リポジトリの外へ出る操作のため、承認をお願いします。

## 3. 対策C：指示書の自己変更への対策（案のみ・未実施）

### 前提

- オウルの指示書（`docs/owl/AGENTS.md`）には、「書き換えは常時認可」と書かれています（§10）。これが今回の変更の根拠になり得ます（推測。親方の確認が要ります）。

### 案C1：実行後に検知し、指示書の変更は適用せず保留する（推奨）

- **やり方**：
  1. Codexの実行後、指示書（`AGENTS.md`、`CLAUDE.md`、`docs/*/AGENTS.md` など）に差分があるかを確認します。
  2. 差分があれば、その変更を取り込まず、案2の退避ブランチへ保存します。作業ツリーの指示書は元に戻します。
  3. 報告書に「指示書の変更を保留」の節を作り、**変更箇所の要点（追加・変更・削除）を必ず載せます**。
  4. 承認されるまで、指示書の変更は適用しません。
- **良い点**：Codexの実行を止めずに、指示書の変更だけを確実に止められます。
- **危ない点**：Codexは実行中に指示書を読んで動くため、変更されたルールで作業した分は残ります。検知は実行後になるため、その回の作業結果も合わせて確認が要ります。
- **作業時間の目安**：2〜3時間（推測）

### 案C2：Codexの実行時に指示書を読み取り専用にする

- **やり方**：Codexの実行設定で、指示書だけを書き込み禁止にします。
- **良い点**：書き換えそのものを防げます。
- **危ない点**：Codexの設定で、ファイル単位の読み取り専用ができるかは**未確認**です。できない場合は実装できません。
- **作業時間の目安**：不明（調査が先に要る）

### 推奨

- **C1を実施する**（検知と保留は今の仕組みで実装できるため）。
- C2は、Codexの設定でできるかを別途調べてから判断します。

### 共通ルールへの一文（案）

親方が承認したら、共通ルールに次の一文を入れることを案として出します。

> 指示書（AGENTS.md・CLAUDE.md などAIの行動ルールを書いたファイル）の内容を変えるときは、変更案を報告書に書き、実施は親方の承認後に行う。

- 注意：オウルの指示書 §10 の「書き換えの常時認可」とは矛盾します。この一文を入れる場合は、§10 も合わせて直す必要があります（親方の判断）。
- 今回は、オウルの指示書も共通ルールも**変更していません**。
