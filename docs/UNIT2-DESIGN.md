# 二号機エージェント設計書

作成：2026-11-21 ／ モコ
状態：設計のみ。実装はごとうの判断待ち。

## 目的
ごとうがモコに指示すると、PC上の二号機（Claude Code／Codex）が作業を実行し、モコが検収して報告する仕組みを作る。ごとうはコピペや進捗の見張りをしなくてよい状態にする。

## 大前提（境界）
1. **法律に反する自動化はしない**（最重要の境界）。サービスの規約は「禁止と明記されている内容はしない」が基準。禁止の明記がないことは過度に慎重にならず前向きに進める。ただしアカウント停止など重大なリスクが見込まれる場合は、事前にごとうへ伝える
2. なるべく課金しない。既存プラン（Claude Code・Codex）と無料の仕組み（agmsg、セルフホストのn8n）を優先。有料ルートが必要なら、事前に費用を明示して承認を得る
3. お金・対人・外部公開・インフラ変更は、実行前にごとうの承認を得る
4. 「できない」作業に当たったら、①なぜできないか（権限・道具・情報のどれが足りないか）を切り分け、②足りない部分を補う設計を先に出す。無理な場合は代替案を出す

## 構成
- **モコ**：窓口。指示の分解、依頼の作成、検収（完成と言えるかの判定）、ごとうへの報告
- **連絡経路**：GitHub の inbox 方式（モコ⇔二号機）。PC内のAI同士は agmsg（SQLite経由、リアルタイム）
- **二号機**：PC上の Claude Code／Codex。専用の作業場所に「指示書・記憶・スキル」を持つ
- **n8n**：定期実行やサービス連携の接着剤（必要になったら使う）

## 二号機の持ち物
- 指示書（CLAUDE.md／AGENTS.md）：役割、守るルール、承認なしで進めてよい範囲、止まるべき場面
- 記憶フォルダ：やったこと・学んだこと・プロジェクト別の状態をファイルで蓄積する
- スキル群：繰り返す作業を手順化（SKILL.md）して増やしていく

## 共有メモリ（他のAIと記憶を共有する）
- 正本は既存の **Drive「モコ知識ベース」（Obsidian Vault）** を活用する。新しく別の置き場所は作らない（2026-11-21、ごとうの意向）
  - Notion＝業務の正本、モコ知識ベース＝AI共有の記憶スペース、という既存の役割分担のまま
  - モコは Drive 経由で読み書きする。PC側のAI（Claude Code・Codex）は、PCに同期されたDriveフォルダ経由で読み書きする想定（PC側の同期の有無は実装時に確認する）
  - GitHub の inbox 側に置くのは作業の受け渡し用ファイルだけにし、長期の記憶はモコ知識ベースへ集約する
- 書き方ルール：モコ知識ベースの既存ルール（00_共通ルール）に従う。既存内容は消さない、追記は日付と名前を付ける、推測で書かず不明は「要確認」
- モコの内部メモリそのものは共有されない。モコは「共有してよい学び・決定事項」をモコ知識ベースへ書き出し、他のAIの書き込みも読んで自分の判断に使う
- agmsg はその場の連絡用、共有メモリ（モコ知識ベース）は長期の記憶用と使い分ける

## 運用フロー
1. ごとう → モコに指示
2. モコが作業を分解し、依頼ファイルを作る（承認が要る作業は先にごとうへ確認）
3. 二号機が実行し、結果と証跡（変更ファイル・ログ）を返す
4. モコが検収する。基準に届かなければ直しを再指示する
5. モコがごとうへ「完成／未完成（理由）」をはっきり報告する

## 仕上がってもできないかもしれないこと（正直な限界）
- PCの電源が切れている・スリープ中は二号機は動かない
- モコ→二号機への指示反映は最大30分ほど遅れる（ワーカーの実行間隔。短縮は可能だが、常時接続ではない）
- 本人確認・SMS認証・CAPTCHAなど、本人の操作が要る場面では止まる
- 規約に「禁止」と明記されている自動化はしない（例：自動操作が明示的に禁止されているサービスへの自動投稿）。その場合は「下書きまで自動＋最後は本人」の形に落とす。禁止の明記がないものは、この限界には含めない
- ChatGPTのウェブ版の自動操作（APIなしでは正攻法がない）
- 物理的な作業・現場作業
- スマホアプリの中でしかできない操作（公式LINEアプリ内の操作など）は、PC側からも直接は触れない

## モコにはできないが、二号機にはできること（例）
- PC内のファイルの直接の読み書き（OneDriveの作業フォルダ、GitHub未pushのプロジェクトなど）
- PCにインストール済みのソフト・コマンドの実行（ビルド、テスト、画像処理パイプラインの実行など）
- 長時間・大量の処理をPCで回し続けること
- ローカルで動く n8n や Docker コンテナの操作
- PC内のAI同士のリアルタイム連携（agmsg）の参加者になること
- ローカルのGitリポジトリでのコミット・ブランチ作業

## 知識ベースの運用（将来像）
- 各AIは定期的にモコ知識ベース（Obsidian／Notion）へ記憶を書き込む。PC側のAIにはその設定が一部あるが、現状はあまり進んでいないため、実際に動いているかの確認と立て直しを実装時の確認項目に入れる
- 各AIは作業を始める前に正本（モコ知識ベース／Notion）を参照してから動く。この習慣を各AIの指示書に明記する
- 蓄積された記憶は、仕事をスムーズに進めるためだけでなく、新しいアイデアの発想の元としても使う。モコは定期的に内容を整理・要約し、気づいたアイデアをごとうへ提案する役割を持つ
- この環境の設定と維持はモコが主導する（2026-11-21、ごとうの意向）

## ハチの形：モコの部下・役割別の複数ハチ（依頼029、2026-11-22の親方の考え）
- ハチは1人で何でもやる形にせず、**モコの部下として役割別の複数のハチ**に分ける。
- **モコが司令塔**：仕事の割り振り、報告の受け取り、検収、親方への報告。
- 最初は3役（増やしすぎない）：
  - **アント（実行）**：作る・直す・調べる（agmsg、n8n、ふく1など）
  - **ハチ（見張り）**：自己検知・自動修理（機能1）、健康診断、詰まりの検知
  - **オウル（検収）**：アント（実行）の仕事を検査し、報告を書く（PDCAのC）
- 後から足す候補：調査係、記録係（知識ベースの整理）。名前は未定で、候補はゾウ・カメ（記録係）、カラス・キツネ（調査係）。
- 設計で守ること：
  - 役割ごとに担当フォルダ・受け持ちを分け、同じファイルを同時に触らない。
  - 連携は agmsg と GitHub 経由。取りまとめはモコ。
- 役割ごとの名前・指示書（CLAUDE.md・AGENTS.md）の分け方は、計画書 `docs/UNIT2-PLAN.md` 12章。
- 名前（依頼030・031）：見張り係の名前は「ハチ」。表示は必ず「名前（役割）」の形（例：ハチ（見張り））。報告書・ボード・設計書すべてで統一する。

## 実装の段階（案）
- 第1段階：二号機の置き場所・指示書・記憶の雛形を作り、今のワーカーで試運転する
- 第2段階：agmsg で二号機内のAI連携を有効化し、スキルを増やす
- 第3段階：n8n とつないで、定期作業（楽天ROOM・Pinterest投稿の下準備など）を自動化する
