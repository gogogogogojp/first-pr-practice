## 1. 受信の正本は郵便受け（SQLite）

- **決定案**：受信の正本はSQLiteの郵便受けとする。プッシュ通知は補助とする。
- 通知が届かなくても、次のタイミングで郵便受けを確認する。
  - 起動時
  - 作業の区切り
  - 期限の直前
- 理由：通知は届かないことがあるため、通知だけに頼ると相談を取りこぼす。

**完了条件（Codex原文）**：**P0｜自動返信の停止または差し替え**：承認済みの組み合わせだけが送信分岐に到達し、送信失敗や結果不明時の状態が成功と区別され、本文が運用ログに残らないこと。

**検証の案（モコ案・Codex原文ではない）**
- 通知を止めた状態で、郵便受けに置いた相談を起動時の確認で拾えること。
- 拾えなかった時に「未受信」と表示されること。

## 2. 登録と通知先の寿命を分ける

- チームとメンバーのIDは維持する。
- 通知先（プッシュ先）は、セッションの世代と有効期限を持たせる。
- 無効化するのは、**終了が確認できた世代だけ**とする。
- 「欠落（登録が無い）」と「判定不能（確認できない）」は区別して書く。判定不能は無効化しない。
- パス表記は正規化して保存し、二重登録を防ぐ。
- プッシュ先は**一つに決める規則**を置く（同時に複数の通知先へ送らない）。

**完了条件（Codex原文）**：**P1｜登録と通知先の寿命**：旧セッションの終了処理が新しい通知先を消さず、古いパス表記で二重登録されず、同じ欠落のログが連続出力されないこと。

**検証の案（モコ案）**
- 同じパスを表記違いで2回登録しても、登録は1件になること。
- 終了が確認できていない世代は、無効化されないこと。

## 3. 受信確認と相談の処理を分ける

- 既読とは別に、次の項目を持つ。
  - 相談ID
  - 返信先ID
  - 期限
  - 処理状態
- 「返信の受理」と「期限切れ」は、どちらか一方だけが確定する。
- 再試行は**同じ送信キー**を使い、重複を防ぐ。
- 相談の本文は**意見として扱う**。操作の承認には使わない。

**完了条件（Codex原文）**：**P1｜受信確認と相談の処理を分ける**：通知なし・返信と期限の競合・送信直後の中断・再読込の各経路で、有効な返信と処理結果が重複しないこと。

**検証の案（モコ案）**
- 同じ送信キーで2回送っても、処理は1回になること。
- 期限切れの後に返信が来ても、状態が二重に確定しないこと。

## 4. 常駐・Windows対応・チーム境界

- **常駐しない場合**：受信は起動時と待機時の確認に寄せる。
- **Windows対応**：BashからWindows側へ渡す境界で、パスを変換する。参考は `team-list.sh` の `cygpath -m` による変換（`reports/2026-11-23_agmsgのteam-list修正.md`）。
- **チームの分け方**：役割ごとではなく、次の境界で分ける。
  - 案件
  - 権限
  - 本番と試験

**完了条件（Codex原文）**：**P2｜常駐・Windows対応・チーム境界**：端末で使える機能が判別でき、別チームへの誤配送を防ぐ条件があり、滞留・通知失敗・ログ容量を本文なしで監視できること。

**検証の案（モコ案）**
- Windowsのパス（`C:\...`）を渡しても、Python側で読めること。
- 本番と試験のチームが、同じ郵便受けを共有していないこと。
